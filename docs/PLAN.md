# 웹 OS 기획서

- 작성일: 2026-11-25
- 상태: 구현 중 (6단계 일부까지 완료, 아래 진행 상황 참고)
- 목적: 포트폴리오용 장기 프로젝트 (6개월 이상)

## 1. 콘셉트

**브라우저 탭 안에서 실제 컴파일된 프로그램이 프로세스로 돌아가는 OS.**

대부분의 웹 OS는 창 모양의 UI 컴포넌트 모음이다. 이 프로젝트는 커널이 WASI(WebAssembly 표준 시스템 인터페이스)를 구현해서, Rust나 C로 짠 프로그램을 수정 없이 컴파일해 올리면 그대로 실행되게 한다. "ls를 흉내 낸 함수"가 아니라 진짜 `ls` 바이너리가 돈다.

### 결정 사항

| 항목 | 결정 |
|---|---|
| 핵심 차별점 | 진짜 커널 구조 (프로세스 격리, 시스템 콜, VFS, 파이프) |
| 디자인 | 모던 미니멀 자체 디자인. 특정 기존 OS의 외형을 따라 하지 않는다 |
| UI 스택 | SolidJS + TypeScript + Vite |
| 커널 | TypeScript (전용 Worker에서 실행) |
| 유저 프로그램 | Rust → WASM (WASI 타깃) |
| 기간 | 6개월 이상 |

## 2. 구조

```
┌─ 메인 스레드: 디스플레이 서버 ────────────────┐
│  창 관리자 · 합성 · 입력 전달 (SolidJS)        │
└──────────────┬───────────────────────────────┘
               │ 메시지
┌─ 커널 Worker ┴───────────────────────────────┐
│  프로세스 테이블 · 스케줄링 · 시그널           │
│  VFS (메모리FS / OPFS 영구저장 / procfs / devfs)│
│  파이프 · 파일 디스크립터 · TTY                │
└──────────────┬───────────────────────────────┘
               │ 시스템 콜 (SharedArrayBuffer + Atomics)
┌─ 프로세스 Worker × N ────────────────────────┐
│  WASM 바이너리 (셸, coreutils, 유저 프로그램)  │
└──────────────────────────────────────────────┘
```

### 핵심 설계

- **블로킹 시스템 콜.** 프로세스가 `read()`를 부르면 요청을 SharedArrayBuffer에 쓰고 `Atomics.wait`로 실제로 멈춘다. 커널이 처리한 뒤 `Atomics.notify`로 깨운다. 동기식으로 짜인 기존 프로그램이 그대로 동작하는 이유다.
- **프로세스 격리.** 프로세스 하나가 무한 루프에 빠져도 UI가 멈추지 않는다. 작업 관리자에서 `kill`하면 해당 Worker가 실제로 종료된다.
- **GUI 앱.** 화면은 메인 스레드 컴포넌트가 그리고, 로직은 Worker 프로세스에서 돌며 CLI 프로그램과 같은 시스템 콜을 쓴다. 캔버스가 필요한 앱은 OffscreenCanvas를 프로세스에 넘긴다.
- **가상 파일시스템.** 마운트 지점별로 구현을 바꿔 끼운다: 메모리FS(`/tmp`), OPFS(`/home`, 새로고침 후에도 유지), procfs(`/proc`), devfs(`/dev`).

### 스택 선택 이유

- **SolidJS:** 창 드래그·리사이즈처럼 초당 수십 번 바뀌는 상태를 가상 DOM 없이 해당 노드만 갱신한다. 창이 많아져도 버벅임이 적다.
- **커널은 TypeScript:** Worker, SharedArrayBuffer, OPFS 등 브라우저 API를 직접 다루는 계층이라 가장 자연스럽다.
- **유저 프로그램은 Rust → WASM:** 셸과 기본 명령어를 Rust로 작성한다. 커널이 표준 인터페이스를 구현했다는 증거가 된다.

## 3. 로드맵

| 단계 | 기간 | 결과물 |
|---|---|---|
| 1. 커널 뼈대 | 1개월 | Worker 프로세스 생성·종료, 시스템 콜 통로, 메모리 파일시스템, "hello world" WASM 실행 |
| 2. 터미널과 셸 | 1.5개월 | TTY, 파이프, 리다이렉션, 환경 변수, Rust로 짠 셸과 명령어 10여 개 |
| 3. 디스플레이 서버 | 1.5개월 | 창 관리자, 포커스, 스냅, 런처, 디자인 시스템 |
| 4. 시스템 앱 | 1개월 | 파일 탐색기, 텍스트 에디터, 작업 관리자, 설정 |
| 5. 영구 저장과 `/proc` | 2주 | OPFS로 새로고침 후에도 파일 유지, `cat /proc/1/status` 동작 |
| 6. 포트폴리오 연결 | 2주 | 부팅 화면, 이력서·프로젝트 앱, 첫 방문자용 안내, 모바일 간소화 화면 |
| 7. 확장 (선택) | 이후 | 패키지 매니저, 에뮬레이터 앱, 자체 언어, 네트워크 스택 |

1~2단계는 화면에 보이는 것이 터미널뿐이지만 차별점의 전부가 여기에 있다. 창부터 만들면 평범한 웹 OS로 끝나므로 순서를 바꾸지 않는다.

### 1단계 완료 기준

- Vite + Solid + TS 프로젝트와 Rust 워크스페이스가 한 저장소에서 빌드된다.
- 커널 Worker가 WASM 바이너리를 프로세스 Worker로 띄운다.
- 프로세스가 블로킹 시스템 콜로 표준 출력에 쓰고, 종료 코드가 커널에 전달된다.
- 메모리 파일시스템에서 파일 열기·읽기·쓰기·닫기가 된다.

### 진행 상황 (2026-11-25 기준)

| 단계 | 상태 | 기획과 달라진 점 |
|---|---|---|
| 1. 커널 뼈대 | 완료 | Solid는 빌드 플러그인 호환 문제로 1.9 사용 |
| 2. 터미널과 셸 | 완료 | 터미널 화면을 라이브러리 없이 직접 구현. 줄 편집기(이력, 탭 자동완성)와 키 단위 입력 모드 추가 |
| 3. 디스플레이 서버 | 완료 | 독 대신 왼쪽 세로 레일. 창 전환 단축키와 창 배치 저장은 없음 |
| 4. 시스템 앱 | 완료 | 화면 앱은 프로세스가 아니라 메인 스레드에서 돌며 커널에 파일 작업을 요청한다. 프로세스별 CPU 사용량은 없음 |
| 5. 영구 저장과 `/proc` | 완료 | OPFS 직접 마운트가 아니라, 메모리에서 읽고 쓴 뒤 바뀐 부분만 OPFS로 옮긴다. 범위는 `/home`이 아니라 전체 디렉터리(`/proc` 제외, `/tmp`는 켤 때 비움). `/proc/self` 없음 |
| 6. 포트폴리오 연결 | 일부 | 부팅 화면, 첫 방문 안내, 휴대폰 화면은 완료. **이력서·프로젝트 소개 앱은 보류** (내용이 준비되면 추가) |
| 7. 확장 | 진행 중 | 시스템 콜 추적 앱, `top`·`vi`(전체 화면 프로그램) 완료 |
| 창을 여는 프로세스 | 진행 중 | 원래 구조(§2 "GUI 앱")로 돌아가는 작업. 프로세스가 창을 열고 그리기 명령을 보내고 입력을 받는 시스템 콜과, 그 위에서 도는 첫 프로그램인 그림판(`paint`) 완료. OffscreenCanvas를 넘기는 대신 그리기 명령을 보내는 방식으로 했다. 기존 화면 앱(메모 등)을 프로세스로 옮기려면 글 입력 칸·스크롤·그림 표시가 규약에 더 필요하다 |
| 장기 사용 대비 | 진행 중 | 기획에 없던 항목. 영구 저장 요청과 저장 상태 표시, 한 번에 한 탭만 실행, 로컬 보관 폴더(전체 디렉터리를 실제 폴더에도 저장하고 거기서 복원), 백업 파일(tar) 내보내기·되살리기, 저장소 유실 알림까지 완료. 앱 설치(PWA)는 배포 때로 미룸 |

## 4. 방문자가 보게 될 장면

1. 부팅 로그가 흐른다. 연출이 아니라 실제 커널 초기화 로그다.
2. 터미널에서 `cat resume.md | grep -i rust | wc -l`이 동작한다.
3. `yes > /dev/null &`을 돌리면 작업 관리자에 CPU를 먹는 프로세스가 뜨고, 종료하면 사라진다.
4. 직접 컴파일한 `.wasm` 파일을 창에 끌어다 놓으면 실행된다.

4번이 이 프로젝트만의 한 방이다.

## 5. 제약과 범위

- **호스팅:** SharedArrayBuffer는 교차 출처 격리 헤더(COOP/COEP)가 필요하다. Cloudflare Pages, Vercel, Netlify는 헤더 설정이 되고, GitHub Pages는 우회책이 필요하다.
- **모바일:** 데스크톱형 UI라 휴대폰에서는 별도의 간소화 화면을 제공한다 (6단계).
- **`fork()` 미지원:** WASM에서는 구현이 매우 어렵다. 프로세스 생성은 `spawn` 방식만 지원한다.
- **외부 리소스:** 교차 출처 격리 상태에서는 외부 이미지·스크립트 로딩이 제한되므로 자산은 모두 같은 출처에서 제공한다.
